# Nutrilog – project notes for Claude

Calorie, macro and micronutrient diary as a static PWA. No build step, no server, no framework.
Owner: Norbert, a Hungarian service designer who is a beginner at coding. Reply in Hungarian, address him as Norbert,
explain every manual step (GitHub clicks, phone steps) in small numbered steps with the exact English button names.

## Hosting
- Repo `norbert-vincze/Nutrilog_PWA`, branch `main`, served by GitHub Pages from the root folder (public repo).
- Live: https://norbert-vincze.github.io/Nutrilog_PWA/ . A push is live after 1–10 minutes (Actions → "pages build and deployment").

## Decisions already made with Norbert – do not undo
- UI is English, sentence case. Food input and search understand Hungarian and English (`DICT`, `PHRASES`, `singular()` in app.js).
- Names: tabs Diary / Nutrients / My foods / Data; actions **Log food**, **Scan**, **Create food**; one term per nutrient everywhere (Carbohydrate, not Carbs).
- Look: Revolut-inspired fintech style (big number, circular actions, grey cards, bottom sheets, light/dark). Do not copy the brand.
- Meals are `Meal 1` … `Meal N`, count set by `MEAL_COUNT` (6). No breakfast/lunch names. A new entry defaults to the meal of the latest entry on the shown day (Meal 1 on an empty day).
- Every diary entry has a time of day: `tm` ("HH:MM", local, 24 h), editable in the Amount/Edit entry sheet (`#tm`, next to Meal). Since version 13 `#tm` is a **plain text field** (`type=text inputmode=numeric maxlength=5 placeholder=HH:MM`, label "Time (24 h)"), not `<input type="time">`: iOS follows the phone's 12/24 h setting for the native picker and ignores `lang`. `shapeHm()` shapes the typing (digits only, colon added after two digits, `1745` becomes `17:45`), `normHm()` pads on blur/save (`8:30` becomes `08:30`), `validHm()` checks 00:00–23:59 and the error sits next to the field. New entries start at the current time. Entries without `tm` (made before version 6) show the time they were added (`t`, never changed). The time never moves an entry to another day (`d` stays the shown day). Within a meal entries are sorted by time (`byTime`); `defaultMeal()` still uses the creation order `t`. The entries CSV has a `time` column after `date`. Do not call `focus()` on the time field outside the tap (iOS); the select-all on focus runs 40 ms after the tap.
- Theme is a manual setting: Data tab → **Appearance** → Auto / Light / Dark (`localStorage` key `nutrilog.theme`, not part of the backup). CSS has only `:root` (light) and `:root[data-theme="dark"]`; there is no `prefers-color-scheme` block. `data-theme` is always set to `light` or `dark`: first by the inline script in `index.html` (before first paint, no flash), then by `applyTheme()` in app.js, which also follows live phone changes while Auto is on. Keep the rule in both places identical. The `theme-color` meta is a single tag updated by script.
- USDA is a second source of generic foods next to CIQUAL (Norbert asked for it after seeing that kaloriabazis.hu uses USDA). It is bundled, not a live API: the FDC API needs a key in every request and deactivates keys found in public repos. Search sheet order: My foods, CIQUAL, USDA (10 rows, "Show more USDA results" adds 30), Open Food Facts. USDA foods: id `usda:<fdc_id>`, `src:'usda'`, tag USDA, 100 g basis, no Edit food, household measures from FDC as buttons but the amount still starts at 100 g (`startPortion`). The search uses the same DICT (Hungarian) but not PHRASES, and matches plurals ("Apples"). Id prefixes: `c:` CIQUAL, `usda:` USDA, `o:` Open Food Facts, `u:` foods you create (never reuse `u:` for anything else). Missing stays missing: only salt (from sodium), crude protein (nitrogen x 6.25), vitamin D from IU and energy from kJ/Atwater are derived, see the docstring of the converter. Fatty acids use exact isomers only, vitamin K2 is MK-4 only. If `usda.json` cannot load, the app starts without it and the Diary says how many entries are hidden.
- NOVA (food-processing group 1–4) has a summary card on the Nutrients tab, above the nutrient groups (`novaHtml`, container `#nova`), plus a fold "Set NOVA groups" where the group is set by hand. The share is of **energy** (kcal, lower value) and counts only entries with energy data; they are reported in the coverage line (`noEnergy`). Unknown stays unknown: **nothing is guessed** (no mapping from CIQUAL/USDA food groups), CIQUAL and USDA foods start "Unclassified". `novaOf(food)` is the one place that gives the effective group (Diary banner, card, CSV `nova` column all use it); `setNova(food, v)` writes it: foods in `S.foods` (`u:` and `o:`, `src` user/off) keep it in `food.nova` (the same field as the NOVA select in Edit food, and the group Open Food Facts delivers; a hand choice overwrites it), CIQUAL and USDA foods keep it in `S.meta.nova[food id]` (backup JSON includes `meta.nova`; `metaDefaults()` is the single source of the meta shape, used at start, in `init()` and in `importJson`, so old backups without `nova` still load). Tapping the chosen number again clears it, every change has an Undo toast. The list re-draws only `#nova` (`refreshNova`) and its open state is kept in `novaOpen`, because replacing the whole view would close the fold after each tap. Shares are whole percents that add up to 100 (`sharePct`, largest remainder), below 1% shows `<1%`. NOVA group names and examples are the `NOVA` constant (flour is group 1, not 2).
- dmBio is a third packaged-food source, built in, not a live API. Id `dm:<dm article id>`, `src:'dmbio'`, tag dmBio, 100 g basis, no Edit food, amount starts at 100 g (`startPortion`), NOVA stays "Unclassified" (nothing guessed; set by hand in `S.meta.nova`). Search sheet order: My foods, **dmBio** (10 rows, "Show more dmBio results" adds 30), CIQUAL, USDA, Open Food Facts. `searchDm` matches Hungarian names, accent-free; typed English words are mapped back to Hungarian stems (reverse `DICT`, plus `DM_EN`); words under 4 letters match only at a word start (`egg` must not find `meggy`); if no product has a word it is dropped; a barcode (6+ digits) is an exact match. A dmBio barcode (12/13-digit variants) is found offline in `runOff`, after your own saved foods and before Open Food Facts. If `dmbio.json` cannot load, the app starts without it and the Diary says how many entries are hidden (`DM_ERR`).
- **Estimates are marked, label values are not.** (Own foods can carry estimates too: see the version 14 bullet below.) Every non-null dmBio value whose index is not in the food's `l` (`_lab`) is an estimate (CIQUAL-based, confidence `q`: h/m/l/v/n = high/medium/low/very low/none). `isEst`, `energyEstimated`, `trackedEst` are the one place that decides; `totalsFor` returns `est` (count per nutrient) and `estNames`. The Nutrients tab puts `~` before such values, the detail line says "Estimate, not a label value: name (confidence)", the Amount sheet has the fold "Estimated values · confidence X" (`dmInfo`), and the CSV has `estimate_confidence`, `energy_estimated` and `<nutrient>__est` columns (only for nutrients that are estimated somewhere). Energy that is a label value is not marked. Fortified products (`f:1`, 19) keep their estimates but the fold warns they can be too low. dm products without a dm table (rules R6/R6e) have no label values; confidence "none" products have no values at all. The converter adds portions that follow from the method note only: `100 ml`, `1 tbsp (15 ml)`, `1 tsp (5 ml)` (R8, weight of the volume) and `100 ml prepared`, `0.5 l prepared` (R7, grams of dry powder).
- **Sync (optional, version 12)** keeps the diary in a private GitHub repository of the user (for Norbert `norbert-vincze/nutrilog-data`, made by hand; the README tells him to tick "Add a README file"). Norbert chose this (option B) over a cloud database with login (Supabase/Firebase); friends use the app with their own data or their own repository, nothing of other people is stored centrally. GitHub REST API from the browser with a fine-grained token (Contents: Read and write, one repository). Settings and state live in Store key `sync` (`SY`: `cfg` with the token, `rec`, `shas`, `last`, `born`, `info`), never in `S`, never in the backup JSON, never in the repository. The app refuses a repository that is not private (`private !== true`) and takes `default_branch` from GitHub.
  - Records: `e:<entry id>` (S.log), `f:<food id>` (S.foods), `p:<food id>` (S.meta.portions), `n:<food id>` (S.meta.nova). `S.meta.last`, `S.meta.backup`, theme and tab are not synced. Files: `entries/YYYY-MM.json`, `foods/0..7.json` (hash of the id mod 8), `meta.json`; format `{app:'tapnaplo-sync', v:1, recs:{key:{u, x}}}`, `x:null` is a tombstone (deletion), kept forever. `validRec` checks every remote record; a foreign file in these places stops the sync with a message.
  - The data records have no time field of their own. `syncStamp()` (called in `doSave()` and at start) compares a canonical hash (`canon`, `hashStr`; keys sorted, keys starting with `_` left out) with the noted one. A changed record gets `u = max(now, old u + 1)` (an edit made after receiving a newer version always wins, even if the clock is slow) and `p:1` (pending); a record that is gone becomes a tombstone. `syncMerge`: the higher `u` wins, equal `u` and different content: the repository wins; same content only keeps the later `u`. Never-synced records get a baseline `u` (`baselineU`: updated, t or created) at connect (`syncRebaseline`), so an old local copy never beats a newer remote one; a remote tombstone wins over them.
  - `syncRound`: `git/trees/<branch>?recursive=1` (HTTP 409 = empty repository) → read the changed files (contents API, raw) → merge **without any `await` between reading and deciding**, so an edit made while waiting cannot be overwritten → write the files with pending records one after another with the sha from the tree; 409/422 means another device wrote first and the whole round repeats (at most 4 rounds). Every `fetch` uses `cache: 'no-store'`: GitHub answers are otherwise cached by the browser for about a minute. Remote changes are applied **in place** (`replaceObj`), so an entry open in a sheet stays valid; then `invalidate()`, `S.log` sorted by `t`, `save()`, `render()` (while a sheet is open: `SY.viewStale`, drawn when the last sheet closes).
  - Triggers: start, `visibilitychange` (more than 20 s since the last run), `online`, every 5 minutes while visible, 4 s after a change (`syncSoon`); the listeners are installed at start even when not connected. HTTP 401/403/404 set `SY.stop` (no automatic retries, "Sync now" tries again, one toast per session); a lost connection is "Offline", not an error. After waiting for the network use `fieldError(input, msg, false)` (no `focus()` outside the tap).
  - "Restore from file" is an intended replace on every device: records missing in the file become tombstones (the confirm text says so while connected). The token is typed by hand on each device; one token per device. Test hooks in `window.__tapnaplo`: `SY`, `syncRun`, `syncStamp`, `syncRecords`, `canon`.

- **Barcode scanner** (`scanBarcode`, ZXing path on iPhone, `BarcodeDetector` where it exists). Norbert's iPhone read a dmBio package (real code 4070765076189) as 6072101076189. Cause, reproduced with his photo: ZXing-js misreads EAN codes when a bar is only about 1.3–2 camera pixels wide, and the wrong number can still pass the EAN check digit; iOS gives 640x480 unless asked; the first reading was accepted at once. Fixes that stay: (1) `getUserMedia` asks for `width/height ideal 1920x1080`, `facingMode ideal environment`; (2) only EAN-13, EAN-8, UPC-A, UPC-E are read (the QR code dm prints next to the barcode was read as a "barcode"); (3) `MultiFormatReader.decode(image, hints)` **forgets the hints after every call**, so pass `hints` in every call (`setHints` once does nothing); (4) a number is accepted by `vote()` only after it was read 3 times in the last 10 readings (2 times when one bar is at least 2.5 camera pixels wide, computed from the two result points, 92 bars apart; 2 times with `BarcodeDetector`) and no other number was read twice; (5) the loop looks about every 120 ms (quick look each frame, `TRY_HARDER` only on every 3rd failing frame because it is 10x slower). Voting cannot catch a systematic misread (the same wrong number again and again at about 1.3 px), so the resolution matters most. The not-found message says that the camera may have misread the number. Do not go back to `BrowserMultiFormatReader.decodeFromConstraints`.
- Barcode lookup is worldwide (Open Food Facts v2 by code). HTTP 404 means "not in the database", not an error. 12-digit and 13-digit variants are tried. A saved food with the same barcode wins and works offline. The Hungary filter applies only to name search and is opt-in.
- Liquids are treated as grams (1 ml ≈ 1 g).

## iPhone gotchas (learned the hard way)
- Never call `focus()` outside the tap that started the action. On iOS it leaves the field "focused" with no keyboard. On touch screens the amount field is not auto-focused (`TOUCH` constant). The amount field always shows its real value (never an empty field with a hidden default); the button says what it will log ("Add 100 g").
- No `window.confirm`/`prompt`/`alert`: they freeze the page in some browsers. Use `askConfirm`/`askText` (in-app sheets) or the Undo toast pattern (diary entries, foods).
- Errors go next to the field (`fieldError`), never only at the bottom of a long sheet. Touch targets are at least 44 px. Text contrast at least 4.5:1 in light and dark (`tests/test_audit_fixes.py` measures it).
- The Create food form shows **Essentials** first; everything else is under **More values**.
- **Field font size is at least 16 px** (`input, select, textarea { font-size: max(16px, 1em); }` in style.css, never an inline font-size on a field): iOS zooms into any field below 16 px when it gets focus and the person has to zoom out by hand. The viewport meta stays `width=device-width, initial-scale=1, viewport-fit=cover`; **never** add `maximum-scale` or `user-scalable=no` (pinch zoom must keep working). `touch-action: manipulation` is set on buttons, links, labels, selects, summaries.
- **Sheets and the keyboard (version 13):** `.sheet-wrap` is `100dvh`. The main buttons of a sheet sit in a `.sheet-actions` row that is `position: sticky; bottom: 0` inside the scrolling `.sheet-b` (the sheet gets `.has-actions`), so Add / Save / Connect / OK stay in view while the form scrolls. iOS does not shrink `dvh` when the keyboard opens, so `fitSheets()` follows `window.visualViewport` (resize and scroll): while a sheet is open, the page is not pinch-zoomed (`scale <= 1.01`) and the visible area is more than 80 px smaller than `innerHeight` (or `offsetTop > 1`), `body.kb` is set and `--vvt` / `--vvh` place the sheet area over the visible part. Put the class `sheet-actions` on the button row of every new sheet. Chromium here has no keyboard; `tests/test_inputs.py` simulates it with a fake `visualViewport`. The real check is on the iPhone.
- **Return key chain:** Create food: Name (`enterkeyhint=next`) → Brand (`next`) → Barcode (`done`, keyboard closes); Amount, Time and the name sheet (`askText`) use `done` and Enter runs the main button (JS `keydown`, no `<form>`); search fields use `search`; Sync setup: repository `next`, token `go`. The decimal keypad on iOS has no Return key, so nutrient fields have no Enter handling. Never call `focus()` in an Enter handler after an `await`.
- The toast (`#toast`) is `position: fixed; left: 50%`, which squeezes its width to half the screen unless it has `width: max-content`. Its Undo button is a 44 px target.
- The active tab is remembered (`localStorage` key `nutrilog.tab`).
- GitHub Pages sends files with a 10-minute browser cache. `sw.js` therefore fetches with `cache: 'no-cache'`.
- `sw.js` keeps the food tables in their own caches (the `DATA` map in sw.js, file → cache name), cache-first, so a new app version does not download them again: `ciqual.json` and `usda.json` in `nutrilog-data-1` (4.9 MB), `dmbio.json` in `nutrilog-dmbio-1`. Raise the number of a cache only when its file changes (the "Reload app files" button clears everything anyway).
- With every change: raise `VERSION` in `app.js` **and** `CACHE` in `sw.js` (same number). The Data tab shows the version and has a "Reload app files" button (clears service worker and caches, keeps the diary).
